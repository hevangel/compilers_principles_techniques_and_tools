Start here

A compiler translates a program from one language into another. Follow one tiny program from source text through tokens, grammatical structure, name resolution, and bytecode. Then run the bytecode on a stack machine and track what each instruction does.

Study Note — Chapters 1 & 2: What is a compiler, and why is it built as a pipeline?

What this chapter is about

A zoomed-out tour of every major stage in a compiler—scanning, parsing, semantic binding, and code generation—using one tiny language before diving into algorithms.

The "Why?" question

Programmers write nested arithmetic and named variables, while a CPU or VM only executes flat instructions on numbered slots or registers. Splitting compilation into stages keeps syntax, scoping, and execution cleanly separated instead of a fragile string-replacement script.

How to study this section

  • Read A tiny compiler and stack machine to trace emit boxes * perbox + 3; end-to-end.
  • Switch between the Rust and Python tabs to compare systems vs. scripting implementations side-by-side.

Scanning and parsing

Scanning groups characters into tokens, such as names and operators. Parsing checks how those tokens fit together according to a grammar. This section covers regular expressions, Thompson/direct automata, DFA minimization, grammar rewriting, top-down and bottom-up parsers, ambiguity resolution, and syntax-error recovery.

Study Note — Chapters 3 & 4: Why split lexical scanning from grammar parsing?

What this chapter is about

Turning raw UTF-8 characters into classified tokens using finite automata, then recognizing nested hierarchical syntax with linear-time deterministic parsers.

The "Why?" question

Finite automata match flat words in linear time without backtracking, but cannot count arbitrary nesting like ((a + b)). Splitting regex-based lexing from context-free parsing (LL(1) top-down and SLR/LALR/LR(1) bottom-up) keeps grammars clean, avoids exponential backtracking, and gives crisp error recovery.

How the 12 examples fit together

  • Lexers & automata: lexer → regex_automata → subset_dfa → dfa_minimize → lex_generator (.l DSL).
  • Top-down parsing: grammar_rewrite (remove left recursion) → ll1 (FIRST/FOLLOW).
  • Bottom-up & generators: slr → lalr → precedence_parse → yacc_generator (.y DSL) → recovery.

Translation and semantic analysis

Semantic analysis resolves names, infers polymorphic types, handles coercions and overloadings, and computes aligned record and array addresses. Syntax-directed translation turns parse trees into DAGs, SSA graphs, three-address IR, switch dispatch, and backpatched jumps.

Study Note — Chapters 5 & 6: How do we check meaning and turn trees into clean intermediate code?

What this chapter is about

Validating rules context-free grammars cannot express (scoping, types, memory alignment) and lowering high-level syntax into Intermediate Representation (IR) such as DAGs, three-address quadruples, and SSA form.

The "Why?" question

A parser accepts x = a + b; as valid syntax even if a is undeclared, mixes incompatible types, or indexes a 2D array that the CPU sees only as raw bytes. Syntax-directed attributes, type inference, and one-pass control-flow lowering turn source syntax into an analyzer-friendly IR.

How the 14 examples fit together

  • Attributes & IR graphs: attributes → sdd_eval → expr_dag → ssa.

  • Control flow & layout: array_layout, record_ir, backpatch, switch_lower.
  • Appendix A capstones: pascal_frontend (1986 Pascal subset) and complete_frontend (2006 block-scoped AST & jumping TAC).

Runtime and code generation

A compiled program needs ways to organize activation records and variable-length stack arrays, collect garbage across generations or incrementally, allocate registers globally, tile expression trees, and emit target instructions.

Study Note — Chapters 7 & 8: How does code manage memory at runtime and map onto finite CPU registers?

What this chapter is about

Designing the call stack (frames, static links, displays), automating heap reclamation (garbage collection), and lowering IR to real target instructions with limited hardware registers.

The "Why?" question

Source code treats memory and temporaries as unlimited, but hardware gives you one call stack, finite heap, and ~8–32 registers. Without disciplined stack links, cycle-safe tracing GC, and smart register allocation/spilling, recursive functions lose outer variables, heaps leak, and loops thrash memory.

How the 9 examples fit together

  • Call stack & scoping: frames (static links) → display_vla (O(1) displays & stack VLAs).
  • Garbage collection: mark_sweep → copying_gc (Cheney & compaction) → generational_gc (write barriers & tri-color).
  • Target codegen: register_codegen (Ershov order) → reg_desc_codegen (getReg) → graph_color_regalloc → dp_tiling.

Optimization and program analysis

Optimizations preserve observable behavior using sound analysis facts: local value numbering, classic bitvector and lattice data-flow frameworks, lazy code motion, loop optimizations, T1/T2 region analysis, modulo scheduling, polyhedral dependence & affine partitioning, and context-sensitive / Datalog-ROBDD pointer analysis.

Study Note — Chapter 9–12: How do we make code faster without changing what it means?

What this chapter is about

Static program analysis (data-flow, loops, scheduling, parallelism, and pointer aliasing) that proves mathematical facts across every possible execution path so transformations stay bug-free.

The "Why?" question

Guessing that a + b hasn't changed or that two loops can run in parallel causes silent miscompilation if a branch or pointer alias disagrees. We need sound conservative rules (may vs. must) that only optimize when proven safe on all paths.

How the 17 examples fit together

  • Local & global data-flow: value_numbering → liveness, reaching_defs, available_exprs, const_prop, lazy_code_motion.
  • Loops & regions: natural_loops → licm_iv → region_dataflow.
  • Instruction & cache parallelism: list_schedule, software_pipeline, loop_locality, dependence_test, affine_partition.
  • Pointers: points_to → context_points_to → datalog_bdd.

Editions and scope

These programs illustrate core techniques across the compiler pipeline using original Rust and Python code and deterministic sample inputs. Chapter numbers point to related reading. A dash means no direct reading is assigned.

  • 1977 Green. Principles of Compiler Design by Alfred V. Aho and Jeffrey D. Ullman. Open Library contents.
  • 1986 Red. Compilers: Principles, Techniques, and Tools, first edition, by Alfred V. Aho, Ravi Sethi, and Jeffrey D. Ullman. 1986 contents.
  • 2006 Purple. Compilers: Principles, Techniques, and Tools, second edition, by Alfred V. Aho, Monica S. Lam, Ravi Sethi, and Jeffrey D. Ullman. Pearson contents.
  • 2014 New International Edition. Aligns chapter-for-chapter with 2006 Purple Chapters 1–11 and Appendices A–B, omitting Chapter 12 as a separate chapter.

See coverage gaps below (or in the repository README) for scope boundaries across editions.

Coverage gaps

This is a concept companion with independently written programs, inputs, and explanations. Core algorithms across all editions' compiler pipeline chapters (Chapters 3–12 and Appendices A–B) are implemented in both Rust and Python, excluding textbook listings, figures, and exercise solutions. The .l/.y DSL generators and Appendix A front-end architectures are covered in self-contained form by lex_generator, yacc_generator, pascal_frontend, complete_frontend, and tiny_compiler.

  • Global trace/superblock scheduling. Chapter 10 covers basic-block list scheduling and cyclic modulo software pipelining, leaving multi-block trace/region code motion across speculative control flow (§10.4) out of scope.
  • Historical survey chapters. Compiler history and architectural surveys (1977 Green Ch. 1–2 language survey and Appendix B; 1986 Red Ch. 11–12 historical compiler notes) have no standalone demos.
  • External C-source emission. Each DSL generator and front end compiles specs directly into in-memory DFA/LALR(1) tables or three-address code interpreters rather than emitting standalone .c/.h toolchain files or full POSIX yacc/flex start-condition ecosystems.
